NOTE ON TEST ISOLATION
DatabaseContext.CreateForTestingAsync() gives each caller its own temp database file, deleted on
dispose. It must NOT go back to a shared ":memory:" database: sqlite-net pools connections by
database path, so every test would share one database. xUnit runs separate test CLASSES in
parallel, so tests then see each other's rows and one test's dispose drops the tables mid-run.
A single test class hides this; it appears as soon as a second class is added.

Service Layer (repositories wired to a real temp DB)
PlannedExerciseService

Adding an exercise with an empty name throws/fails validation
After AddPlannedExerciseAsync, calling ReorderPlannedExercisesAsync produces sequential 1-based ordering
Moving an exercise to a different day (SavePlannedExerciseAsync with oldDay) removes it from the old day and reorders both days
DeletePlannedExerciseAsync leaves remaining exercises with gapless order
Each mutating operation calls IWorkoutNotificationService.ScheduleDailyNotifications() exactly once (mock the notification service)
SavePlannedExerciseAsync passes the saved exercise as `preferred`, so the order number the user
  typed is the position it ends up in
Renaming an exercise carries its logged history with it (logs are keyed by name, so without
  this the history is stranded and the exercise appears to start from zero):
  - rename via UpdatePlannedExerciseAsync moves every matching ExerciseLog to the new name
  - rename via SavePlannedExerciseAsync (the path the UI actually uses) does the same
  - editing only Position or DayOfWeek leaves the logs completely untouched
  - history is NOT moved when another planned exercise still uses the old name -- e.g. the same
    movement planned on Monday and Thursday shares one history, and renaming the Monday entry
    must not take the logs away from the Thursday one
  - a case-only rename ("dips" -> "Dips") still moves the logs, since the log lookup compares
    names with SQL `=`, which is case-sensitive
ExerciseRenamePolicy (pure, no DB needed -- the two rules above, reachable without setting up rows)

IsRename is false for an unchanged name and for a null previous name
IsRename is TRUE for a case-only change ("dips" -> "Dips") -- the log lookup uses SQL `=`, which
  is case-sensitive, so treating these as equal would strand the history
ShouldMoveHistory is true when no other planned exercise answers to the old name
ShouldMoveHistory is FALSE when another day still uses it (Monday renamed, Thursday still
  training "Bench Press" -- the logs belong to Thursday too)
The renamed exercise never blocks its own move: it is excluded by Id, even if the row passed in
  still carries the old name

PlannedExerciseOrdering.AssignSequentialPositions (pure, no DB needed)

Gaps are closed: positions 1,5,9 become 1,2,3
Ties on Position are broken alphabetically by exercise name when `preferred` is null
`preferred`'s Position is a DESTINATION INDEX, not a tie-break. Both directions must be covered:
  - moving UP   (2 -> 1) puts it first and pushes the old occupant down
  - moving DOWN (2 -> 3) puts it third -- REGRESSION GUARD: a tie-break implementation
    silently leaves it at 2, which is the bug this replaced
Out-of-range typed positions clamp: 99 lands last, 0 or negative lands first
`preferred` is matched by Id, not reference (callers pass DB-loaded instances)
An unsaved `preferred` (Id = 0) is still matched, by reference
Only the exercises whose Position actually changed are returned
An already-sequential list returns no changes (so no redundant DB writes)
An empty list returns no changes

Cross-Layer / End-to-End Flows
Full routine setup → workout log: Add exercises to Monday routine → call GetDailyExerciseLogsAsync on a Monday → exercises appear with empty logs
Previous week context: Log a workout on Day N → call GetDailyExerciseLogsAsync on Day N+7 → PreviousDescription reflects Day N data
Progress chart data: Insert 5 logs for the same exercise across 3 dates (multiple on one date) → GetExerciseProgressHistoryAsync returns 3 points with correct max weights
The most valuable tests to write first would be ExerciseLogService.GetDailyExerciseLogsAsync and PlannedExerciseOrdering — these contain the most complex business logic that's easy to break silently.
