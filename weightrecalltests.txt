WEIGHTRECALL — TEST PLAN AND OPEN WORK


== NOTE ON TEST ISOLATION ==

DatabaseContext.CreateForTestingAsync() gives each caller its own temp database file, deleted on
dispose. It must NOT go back to a shared ":memory:" database: sqlite-net pools connections by
database path, so every test would share one database. xUnit runs separate test CLASSES in
parallel, so tests then see each other's rows and one test's dispose drops the tables mid-run.
A single test class hides this; it appears as soon as a second class is added.

== OPEN WORK — deferred decisions and known defects ==

These were TODO comments in the code. Deferred until the workout model settles.

Backup format (WeightRecall.Core/Serialization, Models/BackupData)
  BackupTextFormat.SplitCsvLine does not undo the quote doubling CsvEscape writes. Every quote
    is treated as a delimiter and dropped, so `Farmer's "heavy" carry` restores as
    `Farmer's heavy carry`, and a comma after an embedded quote splits the field in the wrong
    place. Old files are valid CSV — the writer was always correct — so fixing the reader
    breaks nothing.
  BackupData.Version is written on export and never read on import. A file from a future format
    is read as though it were v1, which fails silently: unknown keys are ignored and the
    affected section restores empty.
  BackupData.IsEmpty exists but nothing calls it. BackupService.ApplyAsync deletes both tables
    before inserting, so a file that parses to zero rows wipes everything. Reachable today: any
    .txt with no recognizable section, or a .json of "{}".
  ApplyAsync is not a transaction. A failure between the deletes and the inserts leaves the user
    with neither their old data nor the restored data.
  The .db3 import path copies whatever file was picked over the live database with no validation
    at all — not even a check that it is SQLite with the expected tables.
  SettingsPage.DbPath duplicates the literal in MauiProgram. If one changes, export silently
    targets the wrong file.
  The JSON keys "RoutineItems" / "WorkoutLogs" / "Order" and the matching text section headers
    are pinned to the pre-rename names. Unpin only behind a Version bump that can migrate old
    files.

Database schema
  [Table("RoutineItems")] and [Table("WorkoutLogs")], and [Column("Order")] on
  PlannedExercise.Position, are pinned to pre-rename names. sqlite-net derives them from the C#
  names, so changing them orphans the rows in every installed copy.
  To unpin: PRAGMA user_version plus ALTER TABLE ... RENAME TO / RENAME COLUMN, run inside
  InitializeAsync BEFORE CreateTableAsync (otherwise an empty new table is created first and the
  rename fails), gated on the old table existing in sqlite_master rather than on the version
  number alone — android:allowBackup can restore an old database onto a new install — all in one
  transaction. Keep the backup file format decoupled from this.

Other known defects
  The Progress page labels the window "Last 30 Days", but ExerciseProgressService uses
    AddMonths(-1), a calendar month. Decide which is right BEFORE pinning a test.
  ExerciseLogService.GetDailyExerciseLogsAsync does N+1 queries: one GetLatestLogForExerciseAsync
    per planned exercise. Needs a new repository query, so it is a behaviour change.

== DOMAIN (pure — no database needed) ==

PlannedExerciseOrdering.AssignSequentialPositions
  Gaps are closed: positions 1,5,9 become 1,2,3
  Ties on Position break alphabetically by name when `preferred` is null
  `preferred`'s Position is a DESTINATION INDEX, not a tie-break. Cover both directions:
    moving UP   (2 -> 1) puts it first and pushes the old occupant down
    moving DOWN (2 -> 3) puts it third — REGRESSION GUARD: a tie-break implementation silently
      leaves it at 2, which is the bug this replaced
  Out-of-range typed positions clamp: 99 lands last, 0 or negative lands first
  `preferred` is matched by Id, not reference (callers pass DB-loaded instances)
  An unsaved `preferred` (Id = 0) is still matched, by reference
  Only exercises whose Position actually changed are returned
  An already-sequential list, and an empty list, both return no changes

ExerciseRenamePolicy
  IsRename is false for an unchanged name and for a null previous name
  IsRename is TRUE for a case-only change ("dips" -> "Dips") — the log lookup uses SQL `=`,
    which is case-sensitive, so treating these as equal strands the history
  ShouldMoveHistory is true when no other planned exercise answers to the old name
  ShouldMoveHistory is FALSE when another day still uses it (Monday renamed, Thursday still
    training "Bench Press" — the logs belong to Thursday too)
  The renamed exercise never blocks its own move: excluded by Id, even when the row passed in
    still carries the old name

DailyExerciseLogBuilder
  Build returns the EXISTING log INSTANCE when one is saved for that date, with only its
    PreviousDescription updated — it must not be replaced, or the user's typed values are lost
  Build returns an all-zero placeholder carrying the planned exercise's name when nothing is logged
  FindExistingLog matches on name case-insensitively ("bench press" finds "Bench Press")
  DescribePrevious formats as "Prev: {weight}kg | {sets} sets | {reps} reps"
  DescribePrevious returns NoPreviousData for a null previous log

ExerciseProgressHistory.Summarize
  Several logs on one date collapse to ONE point carrying that date's max weight
  Points come back oldest first
  An empty input returns no points

WeekCalendar  (was DateService; now static, in Domain)
  GetMonday returns Monday for mid-week, for Monday itself, and for the Sunday edge case
  GetDaysOfWeek returns exactly 7 consecutive days starting on Monday

ExerciseLog
  HasRecordedActivity is false only when weight, sets and reps are ALL zero — this is what stops
    untouched placeholder rows being written on every save


== SERVICE LAYER (repositories wired to a real temp DB) ==

PlannedExerciseService
  An empty or whitespace-only name is rejected
  A name is TRIMMED before it is stored ("  Chin UPS " -> "Chin UPS") — logs are matched by
    exact name, so a stray space silently splits the history
  Trimming is NOT treated as a rename: "Squat " -> "Squat" must leave the logs untouched
  A genuine rename typed with untrimmed input still carries its history to the trimmed name
  After AddPlannedExerciseAsync, ReorderPlannedExercisesAsync produces sequential 1-based order
  Moving an exercise to another day (SavePlannedExerciseAsync with oldDay) removes it from the
    old day and renumbers BOTH days
  DeletePlannedExerciseAsync leaves the remaining exercises gapless
  Each mutating operation calls IWorkoutNotificationService.ScheduleDailyNotifications() exactly
    once (fake the notification service)
  SavePlannedExerciseAsync passes the saved exercise as `preferred`, so the typed order number
    is the position it ends up in
  Renaming carries logged history with it (logs are keyed by name, so without this the history
    is stranded and the exercise appears to start from zero):
    via UpdatePlannedExerciseAsync, and via SavePlannedExerciseAsync (the path the UI uses)
    editing only Position or DayOfWeek leaves the logs completely untouched
    history is NOT moved when another planned exercise still uses the old name

ExerciseLogService
  GetDailyExerciseLogsAsync returns one row per planned exercise for that day, in routine order
  GetDailyExerciseLogsAsync looks up "previous" strictly BEFORE the selected date, never the day itself
  SaveExerciseLogsAsync writes only the rows where HasRecordedActivity is true

ExerciseProgressService  (inject a TimeProvider so "today" is fixed)
  The window runs one CALENDAR MONTH back from the injected today, so its length varies:
    2026-09-15 -> 2026-08-15, 2026-03-31 -> 2026-02-28, 2026-01-31 -> 2025-12-31
  Logs outside the window are excluded
  NOTE: settle the "Last 30 Days" label question above before pinning these


== VIEW MODELS (now in Core — fake IDialogService and INavigationService,
   inject a TimeProvider) ==

MainViewModel
  Constructs without touching the database — the load belongs to the page's OnAppearing, and a
    second one started here would race it
  Opens on today, with the current week's Monday–Sunday in the strip
  NextWeek refuses to advance past the current week; PreviousWeek then NextWeek returns
  IsNotToday flips with SelectedDate, and GoToToday clears it
  DeleteLog on an UNSAVED row (Id == 0) removes it WITHOUT prompting
  DeleteLog on a saved row prompts, and a cancelled prompt leaves both list and database intact
  SaveLogs confirms to the user and clears IsBusy

ExercisesViewModel
  Constructs without touching the database; starts on today's weekday
  Add: name plus order saves, closes the popup and clears the fields
  Edit populates the form from the exercise, and PopupTitle/PopupButtonText follow IsEditing
  An EMPTY order adds to the end; when editing, it leaves the position unchanged
  A non-numeric order raises "Invalid Order" and leaves the input intact to be corrected
    (note: the Entry uses Keyboard="Numeric", so this is reachable only via a hardware keyboard,
     paste, or an unusual IME — it is a defensive branch)
  Changing SelectedDay reloads that day's exercises
  Deleting prompts; cancelling keeps the exercise in both list and database
  HideAddPlannedExercise resets IsEditing, IsAddingPlannedExercise and both text fields
